# Report on the Noongar Seasons App

1. The team members who produced the app were Oliver Hunt and Oliver Tegg-Quin. We collaborated through the [GitHub repository](https://github.com/oliver25447884/CITS1501-project-1).

2. This app focuses on the six seasons of the Whadjuk Noongar seasonal calendar. We used Python to create an educational app that presents line graphs of rainfall and temperature for all six Noongar seasons and provides cultural and meteorological context. The app offers another way to understand seasonal timing in Western Australia, where local weather patterns are not always captured by the four-season calendar. It helps users connect daily weather with local seasonal context through an intuitive, information-rich interface.The aim user is anyperson very new to the concept of the noongar seasonal calender, the app does not aim to provide indepth education on the subject rather to provide a gateway to further learning.
3. The application is organised around `main.py`, which creates the shared Tkinter window and connects it to feature controllers in `modules/`. On startup, the security module selects password setup or login; after login, the home page routes users to the season wheel, questions and region lookup, climate report, and sources. For climate analysis, `climate_data.py` reads the two local BOM CSV files, validates and joins rainfall and temperature observations by date, and calculates monthly and annual summaries. `climate_page.py` displays those results and links each month to its season page. The question lookup and climate calculations use `season_calendar.py` so they apply the same month-to-season mapping. The season wheel loads its matching graph and nature-image files from `Data/`; the app's data and visual assets are kept in the project folders. Please refer to ARCHITECTURE.md under the "docs" file for a visualisation
4. The app uses Tkinter for its desktop interface and separates screen presentation from climate-data processing. The climate reader recognises the BOM tables' month columns and ordinal day labels, constructs valid calendar dates, and skips impossible dates such as February 30. It rejects malformed or non-finite measurements, negative rainfall, and temperatures outside its expected range. Blank readings remain missing rather than being treated as zero. Rainfall and temperature dates are joined using their union, so a reading for one measure is retained when the other is absent. The summaries use the arithmetic mean of available maximum temperatures, sum available rainfall, and count days with recorded rainfall above zero. A shared month lookup assigns each month to the Perth-area six-season guide, including Birak across December and January. The seasonal detail pages show supplied PNG graphs; the separate climate page calculates its tables and summary cards from the CSV observations.The code structure uses main.py as the central spine of the app, the additional functions are stored as modual that are imported to main.py. This was done for severa reasons. First, to make it easier to work on the app simultaniusly without stepping on eachothers feet, 2nd to make reading and editing the code easier, rather than scrolling through 1000+ lines of code problems can be identified quicker and easier.
5. Weather data came from the Bureau of Meteorology's Perth Metro site (station 009225) and covers January to December 2024. The dataset contains daily rainfall (millimetres) and maximum temperatures (degrees Celsius). Python code calculates monthly mean temperatures and rainfall totals, then groups the months into two-month Noongar seasons. Calendar months are mapped to the Noongar seasonal guide rather than the four-season calendar. Missing readings are handled by the app, and the data is stored in CSV files for reliable use in Python.

6. The application analyses Bureau of Meteorology data to identify seasonal trends in rainfall and temperature. It also compares adjacent seasons; for example, the app's summaries show that Kambarang has 56.2 mm more rainfall across the season than Birak and a 6.2 °C lower mean daily maximum temperature. This suggests that Western Australia's south-west climate can be described through two-month intervals, including heavy rainfall in Makuru (June and July) and high temperatures in Bunuru (February and March), rather than only through standard three-month intervals. The app presents the temperature and rainfall averages across the 12 months in line graphs. The x-axis is labelled with months and Noongar season categories, while the y-axis shows the measured variable. Blue represents rainfall and red represents temperature.

7. The app is designed to make climate data and Noongar seasonal context accessible to users. It begins with a password screen and a password-recovery option. The main page features an interactive wheel labelled with the Noongar seasons. Selecting a segment opens a page with a line graph, a description of the season's weather, cultural context, and a related nature image. The six season pages share this layout. A questions-and-answers section appears on the main page and covers common user queries. The council lookup displays the associated Noongar region and its map, helping users explore the region connected with their local council. Together, these features create an accessible and educational interface.
8. Nine automated tests in `tests/test_main.py` were run against the application shell, and all passed. They check startup and security-flow setup; normal and screen-constrained window sizing; replacing the active page; routing to Sources, climate, and season features; home-page button actions; and delivery of both lookup questions and FAQs to the question renderer. The climate-data tests additionally cover missing readings, leap-year coverage, impossible dates, malformed values, negative rainfall, missing year headers, and datasets below the required record count. These edge cases are handled by retaining missing values as missing, skipping invalid calendar dates, validating measurements, and clamping requested window dimensions to the display. When climate data cannot be loaded or fails validation, the climate page shows an error and a route back; login and credential-save failures are reported in the security screens. Together, the tests support reliable routing and data handling, although the `main.py` tests use mocked Tkinter widgets and do not verify the real rendered layout, interactive GUI behaviour, or successful desktop launch. In terms of app reliability, the application has no known issues, the previous issue of dissapearing assets has been fixed. Edge- cases are very limited, any inputs are strictly defined, any input outside the approved defianitions simply return an incorrect message.
9. Password setup, login, and recovery are handled locally by the security module. It stores a random salt and a PBKDF2-HMAC-SHA-256 hash (200,000 iterations) for the password and each recovery answer, and compares hashes using a constant-time comparison. Recovery answers are case-insensitive. The credential records are saved as JSON in the user's home folder; the application does not need a remote account service to check them. The climate CSVs and images are loaded from project files, while the council-to-region lookup uses mappings in the application code. Source links open in the user's browser only when selected. The password is limited to six characters and recovery answers to 20, so these limits weaken protection, particularly if someone can access the local credential file and guess short secrets. The app has no account lockout or attempt throttling, and its local credential file is not encrypted by the application. Users should therefore choose non-obvious credentials, protect access to their device, and treat this feature as basic local access control rather than strong account security. Recovery questions were added to address the very real issue of forgotten passwords, these security questions are very generalised questions to avoid asking the user for overly personal information. All Passwords and security question answers are stored locally and are not uploaded to the GIT repository.
10. The app is a Python desktop application built with Tkinter. It uses Python's built-in `csv` module to read Bureau of Meteorology files and the `statistics` module to calculate averages; `datetime` and `pathlib` support date and file handling. Pillow loads and resizes the supplied season-graph and nature-image PNG files. The graphs are stored as image assets, while the climate page reads CSV observations to calculate monthly and annual summaries. This version does not use pandas. Weather data, images, and maps are stored in project folders so the app can display them without an internet connection.
